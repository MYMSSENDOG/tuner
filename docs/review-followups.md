# 코드 리뷰 후속 작업 (2026-08-18)

전체 리뷰에서 나온 항목. 완료하면 체크하고, 근거가 바뀌면 줄을 지우지 말고

## 완료 (2026-08-18) — 1~6

- [x] **1. `SpectralDetector` 실시간 예산 초과** — 1회 검출 30.2ms, 예산
  11.6ms(hop 의 절반). 비용의 90% 가 `core/spectral.py:_dtft_refine` 의
  복소 exp 44만 회(배음 4 × 라운드 3 × 9점 × 4096샘플)였다.

  **해결**: 탐색 그리드가 등차수열이라는 성질을 썼다 —
  `exp(-2j πf t)` 의 인접 주파수 위상자는 공비가 일정하므로,
  `exp(-2j π(f_lo + i·df)t) = exp(-2j π f_lo t) · exp(-2j π df t)ⁱ`.
  (주파수 × 샘플) 쌍마다 지수함수를 부르는 대신 **지수함수 2회 + 누적 곱**
  으로 끝난다(`_dtft_grid_magnitudes`).

  | | 이전 | 이후 |
  |---|---:|---:|
  | 1회 검출 | 30.23ms | **6.14ms** (4.9×) |
  | 예산(11.61ms) | FAIL | **PASS** |
  | 스위트 전체 | 93.9초 | 72.9초 |

  결과는 **비트 단위로 동일**(5개 신호 × 라운드 3/10 에서 차이 0.00e+00)
  이라 주석기(`dtft_rounds=10`)의 정답 데이터도 영향받지 않는다.

  남은 것: 6.14ms 는 여전히 콜백 마감 5.8ms 를 살짝 넘는다. hop 이 1024
  (4콜백)라 평균 부하는 26% 로 충분하지만, 한 콜백이 6ms 막히는 건 그대로다.
  근본 해결은 8번(워커 스레드).

  **(2026-08-23) 이 항목은 앱에서 내려왔다** — 검출기 선택 UI 를 없애면서
  `SpectralDetector` 는 개발 도구 전용이 됐다(`trace --detector spectral`).
  실시간 경로에 남은 건 YIN 1.79ms / 마감 5.8ms 뿐이라 위의 "한 콜백이 6ms
  막히는" 상황은 **제품에서는 더 이상 발생하지 않는다.** 계약 테스트
  (`test_detector_realtime_budget`)는 그대로 둔다 — 도구로 쓰는 것도
  실시간 예산 안에서 도는 게 비교의 전제다.

- [x] **4. `NoteLatch` 재서술** — 클래스 docstring 은 2번에서 이미 실제

  **클래스명은 `NoteLatch` 로 둔다.** "latch" 는 하는 일(이름을 붙든다)을
  정확히 말하고 있고, 틀렸던 건 이름이 아니라 *무엇을 붙드는지*에 대한
  설명이었다. 바꾸면 `NOTE_LATCH_ENABLED` 스위치, 문서 파일명
  (`note-latch-tuning.md`), D-004 참조까지 번지는데 얻는 게 어휘 정확도뿐이다.

## 남은 것 — 곧

- [ ] **10. 음 전환 구간의 지속 글리치** — 6번 작업 중 발견. 오보에 크로마틱
  스케일(C4~B4)의 D#4 → E4 전환에서 **`F6` 가 13프레임(75.5ms) 표시**된다.
  그 구간의 실측 주파수는 325.6 ~ 1385.7Hz 로 요동친다.

  트래커의 점프 확인(2프레임)도, 래치의 dwell(12프레임)도 통과한다 — 13
  프레임이라 한 프레임 차이로 빠져나간다. 새 지표(8프레임)로도, 세그먼트 수
  (13 ≤ 16)로도 안 잡힌다. 검출 단계의 문제라 표시 정책으로는 못 막는다.
  다른 스케일 픽스처에도 같은 게 있는지 먼저 세어볼 것.
