# 메트로놈

**언제 읽나**: 메트로놈의 타이밍·클릭 소리·간섭 억제를 손볼 때, 또는
"앱이 내는 소리를 앱이 다시 듣는" 문제를 다룰 때.

```
▶  -  120  +          ← 창의 컨트롤 줄 아래, 미터 위 (한 줄)
```

v1 은 BPM 과 재생/정지뿐이다. 강박·박자표·세분박·탭 템포는 넣지 않았다 —
필요가 생길 때 만든다(`docs/ARCHITECTURE.md` "미리 만들지 않는다").

## 제1원칙: 박은 오디오 시계 위에 있다

메트로놈이 지켜야 할 것은 하나다. **k번째 클릭이 정확히 k × 60/BPM 초에
있을 것.** 그래서 타이밍을 Qt 타이머에 두지 않는다 — GUI 이벤트 루프는
수~십수 ms 씩 흔들리고 그 오차가 누적되면 드리프트가 된다.

대신 출력 장치가 샘플을 **당겨간다**(`audio/output.py` 의 pull 콜백).
`core/metronome.py` 는 절대 샘플 위치에서 렌더하므로 장치가 블록 크기를
얼마로 잡든 같은 샘플에 클릭이 놓인다.

두 가지 성질이 이 파일의 존재 이유이고 둘 다 테스트로 봉인돼 있다
(`tests/unit/test_metronome.py`):

| 성질 | 어떻게 | 왜 |
|---|---|---|
| **드리프트 없음** | 박 k 를 `origin + round(k × period)` 로 **k 에서 계산**. 직전 박에 주기를 더하지 않는다 | 누적 부동소수 오차는 1분간 안 들리고 10분 뒤 명백해진다 — 메트로놈을 쓰는 시간이 정확히 그 길이다 |
| **블록 크기 무관** | 클릭을 시작 위치에서 섞는다. 호출 사이에 버퍼를 들고 넘기지 않는다 | 장치가 고르는 블록 크기에 소리가 달라지면 안 된다 |

실측: 44.1kHz, 10분, 60/137/208 BPM 에서 마지막 박의 오차 **0.00ms**
(게이트 0.05ms). 블록 64/256/1024/불규칙 어느 쪽으로 나눠도 렌더 결과가
`np.array_equal`.

BPM 을 바꾸면 **지금 울린 박을 기준으로 재기준화**한다(`ClickSchedule.
rebase`). 0번 샘플부터 다시 계산하면 다이얼을 만지는 순간 박이 옆으로
튄다.

## 정답의 출처

이 영역은 `docs/process/ground-truth.md` 의 네 단계 중 1~3 이 공짜다 —
정답이 **산수로 확정**되기 때문이다(음향 루프백 테스트가 성립하는 것과
같은 이유). 주석기도, 제3자 라벨도 필요 없다.

다만 테스트가 스케줄러에게 "박이 어디냐"를 되묻지 않는다. **렌더된 파형에서
온셋을 직접 검출**해 간격을 재고 60/BPM 과 대조한다 — 렌더러가 스케줄에 없는
곳에 클릭을 놓으면 그때 잡힌다.

> 온셋 검출기는 포락선 위에서 돌아야 한다. 클릭이 1000Hz 톤이라 |신호| 에
> 임계값을 직접 걸면 반주기마다 온셋이 잡힌다(60클릭 신호에서 2340개 —
> 실제로 이렇게 발견했다).

## 클릭 소리

1000Hz 사인 20ms, 지수 감쇠 + 끝 4ms 페이드. 파일이 아니라 합성이다
(결정적이고, 픽스처가 아닌 바이너리를 저장소에 넣지 않는다). 시작·끝이
정확히 0 이라 스트림 어디에 섞어도 자기 자신이 불연속을 만들지 않는다.

## 마이크가 클릭을 듣는 문제

메트로놈 소리는 마이크로 들어오고 검출기는 그게 악기가 아니라는 걸 알 방법이
없다. 실측(바이올린 A4 위에 클릭을 섞고 화면 이름의 세그먼트를 셈):

| | 억제 off | 억제 ON |
|---|---|---|
| 120 BPM | `A4 G7 B5 G7 C6 A4 G7 B5` (8) | `A4 A4` (2) |
| 208 BPM | 17 세그먼트 | `A4 G7 A4` (3) |

연주를 쉬는 동안이 특히 나쁘다 — 846프레임 중 154프레임이 `B5`(1000Hz 클릭)
등으로 뜬다. 반대로 **큰 소리로 지속음을 켜는 동안엔 아무 영향이 없다**
(클릭이 묻힌다). 즉 이 기능이 필요한 건 쉬는 구간과 여린 소리다.

### 어떻게 막나

`core/interference.py` 가 "우리가 낸 소리가 이 구간에 들렸나"에 답하고,
엔진은 그렇다면 **검출을 건너뛰고 직전 표시를 유지**한다. 화면을 비우지
않는 것이 중요하다 — 악기는 아무것도 안 변했고 우리가 잠깐 안 봤을 뿐인데,
매 박마다 사라지는 표시는 잠깐 낡은 표시보다 더 나쁜 거짓말이다.

**앱이 쓰는 것은 실시간(`HeardClicks`)이다.** 템포만 받고, 박이 실제로
어디 떨어지는지는 마이크에서 찾는다. 비교 대상인 `ScheduledClicks`(우리가
친 시각을 그대로 씀)는 테스트에서 저울로만 남아 있다.

세 가지가 억제 창의 폭을 정한다:

1. **검출이 실제로 본 구간** = `2 × detector.center_offset`. YIN 은 4096
   버퍼를 들고 다니지만 피치는 최근 2048 에서 읽는다(나머지는 저역 폴백).
   버퍼 길이를 쓰면 대가가 두 배가 된다 — 120 BPM 에서 멈춘 프레임
   **27% vs 15%**.
2. **클릭의 그림자 폭** — 앞 10ms, 뒤 30ms(아래 스윕).
3. 정적 방식에 한해 **출력 장치 지연**을 추정하지 않고 스트림에서 받아온다
   (`AudioOutput.latency_s`). 실시간 방식은 위상을 마이크에서 재므로 이
   숫자가 아예 필요 없다 — 그게 이 방식을 택한 이유 중 하나다.

### tail 스윕

| tail | 120 BPM 세그먼트 / 멈춘 프레임 | 208 BPM |
|---|---|---|
| 20ms | 2 / 14% | 3 / 25% |
| 30ms | 2 / 15% | 3 / 29% |
| 40ms | 2 / 17% | 3 / 32% |

무릎은 20ms 다 — 그 위는 아무것도 못 사고 멈춘 프레임만 늘린다. **그런데
30 을 택했다**: 합성 클릭 뒤에는 방이 없다. 실제 방의 잔향 한 클릭 길이가
가장 싼 보험이고 값은 1~4%p 다. 앱에서 Ctrl+L 로 실제 방 녹음을 뜬 뒤
`tools/promote` 로 재현을 확인하고 20 으로 조일 것.

> 위 표의 `G7` 은 클릭과 무관하다. 클릭이 하나도 없어도 음이 끝나는 감쇠
> 구간에서 나온다(`review-followups.md` 10번과 같은 계열). 억제가 고칠
> 대상이 아니고 실제로 안 고친다.

## 실시간 억제: 템포만 알고 마이크로 찾는다

우리가 친 시각을 안 쓴다. **아는 것은 주기 하나**이고, 위상은 입력에서
찾는다.

### 왜 온셋을 세지 않나

처음엔 레벨 점프로 온셋을 찍고 위상을 맞췄다. 실측이 그걸 죽였다 — 첼로
6초 구간에서 **클릭 14개 중 13개를 찾는 동안 클릭이 아닌 것 17개**를 같이
찾았다. 하나의 트랜지언트를 믿는 위상 추정은 대부분 악기를 따라간다.

그래서 아무것도 지명하지 않는다. **연속 노벌티**(양의 스펙트럼 플럭스,
400Hz 이상)를 주기로 접어 누적한다. 클릭은 매 박 같은 빈에 떨어져 쌓이고,
나머지는 마디 전체에 퍼져 안 쌓인다. 봉우리가 위상이고, 마디 평균 대비
높이가 확신이다.

| | 실측 |
|---|---|
| 락까지 | 정확히 2박 — 40 BPM 3.0초, 200 BPM 0.6초 |
| 락 후 위상 오차 | **5.5ms** (블록 1개 = 양자화 한계) |
| 블록당 비용 | 0.018ms (오디오 콜백 예산 5.8ms) |

### 실악기 × 40~200 BPM

세그먼트 수(괄호는 깨끗한 녹음의 값), `+n` 은 원래 없던 이름이 화면에 뜬 횟수:

| 픽스처 | BPM | 억제 없음 | 정적 | 실시간 |
|---|---:|---:|---|---|
| cello_arco_A3 (3) | 40 / 100 / 200 | 5 / 6 / 10 | 3+0 (4%) / 3+0 (13%) / 3+0 (28%) | 3+0 (2%) / 3+0 (10%) / 3+0 (25%) |
| oboe_scale_C4B4 (3) | 40 / 100 / 200 | 5 / 15 / 24 | 3+0 (4%) / 3+0 (13%) / 3+0 (28%) | 4+1 (3%) / 5+1 (12%) / 5+1 (27%) |
| trumpet_novib_G3 (2) | 40 / 100 / 200 | 2 / 5 / 9 | 2+0 (4%) / 2+0 (14%) / 2+0 (28%) | 2+0 (2%) / 4+1 (12%) / 4+1 (26%) |

실시간이 정적보다 **최대 1개** 더 샌다 — 락이 걸리기 전 첫 두 박이다.
대신 멈춘 프레임이 매번 1~3%p 적다.

### 사는 것: 안 들리면 안 멈춘다

이어폰을 쓰면 클릭은 마이크에 아예 안 들어온다. 그런데도 정적 방식은
스케줄대로 화면을 멈춘다 — 방에 있지도 않았던 소리 때문에.

| | 실시간 | 정적 |
|---|---|---|
| 60 BPM, 클릭 안 들림 | **0% 멈춤** | 8.4% |
| 120 BPM | **0%** | 17.1% |
| 200 BPM | **0%** | 29.0% |

같은 이유로 출력/입력 장치의 시계가 어긋나거나 드라이버가 지연을 틀리게
보고해도 조준이 빗나가지 않고, 남의 스피커에서 나오는 메트로놈도 (BPM 만
알면) 잡는다.

### 갈리지 않는 것 — 알고 넘어가야 할 한계

**템포만 아는 이상 "우리 클릭"과 "박에 맞춰 연주하는 사람"은 구분되지
않는다.** 픽스처 코퍼스 27조합(악기 × 40/120/200 BPM)을 훑은 결과:

| | 봉우리/평균 |
|---|---|
| 클릭 있을 때 최소 | 4.2 (첼로 A3, 200 BPM) |
| **클릭 없을 때 최대** | **86** (스케일 녹음) |

노벌티 대역을 클릭 주파수로 좁혀도, 봉우리의 뾰족함을 봐도 겹친다. 둘 다
"박에 있는 트랜지언트"라서다 — 코드 문제가 아니라 정보의 문제다.

그래서 `LOCK_PEAK_RATIO` 는 **거르는 쪽이 아니라 잡는 쪽으로만** 정한다
(3.0, 실측 최악 4.2 아래로 여유). 사람에게 락이 걸려도 **지금보다 나빠지지
않기 때문에** 감수할 수 있다 — 정적 방식은 박 구간에 뭐가 있든 무조건
얼리므로 연주자의 정박 어택도 똑같이 언다. 실시간은 최소한 **뭔가 실제로
오고 있을 때만** 언다.

정말로 갈라야 한다면 다음 후보는 우리 클릭의 **음색**(1kHz 버스트)을
사전분포에 넣는 것이다. 지금은 안 넣었다 — 사용자가 정한 입력이 "BPM 과
마이크"뿐이고, 아직 그게 부족하다는 실측이 없다.
