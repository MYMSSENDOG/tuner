# D-005: 음향 루프백 테스트 (스피커 → 방 → 마이크)

**영역**: `tests/e2e/test_acoustic_loopback.py` (제거)
**상태**: 제거 (2026-09-06)
**읽음**: 0

## 무엇이었나

정확히 아는 주파수(A4 = 440.000Hz, D5 = 587.330Hz)를 배음 3개 얹어 2.5초
스피커로 재생하고, 같은 시간 동안 실제 마이크로 녹음해, 가운데 절반을
`YinDetector` + `PitchTracker` 에 통과시켜 중앙값 오차 ≤15¢ 와 "옥타브
오검출 10% 미만"을 요구했다.

의도는 **정답의 출처**였다. 다른 실오디오 테스트는 우리 주석기가 매긴
라벨로 채점하므로 앱과 주석기가 같은 방향으로 틀리면 둘 다 통과한다.
음향 경로는 음량·음색을 바꾸고 잔향과 소음을 더하지만 **주파수는 못
바꾸므로**, 재생한 주파수가 곧 정답이 된다.

## 왜 지웠나

**실측(2026-09-06, 개발 기계)**:

| 케이스 | 결과 |
|---|---|
| A4 | **스킵** — "speaker output never reached the microphone (muted or too quiet)" |
| D5 | 리딩 21개(최소 기준 **20**), median +3.3¢, p90 12.2¢ (기준 15¢) |

절반이 스킵되고, 통과한 쪽도 자기 기준을 턱걸이로 넘는다. 스킵 갈래가 셋
(마이크 권한 / 음소거·너무 조용함 / 이어폰이라 음향 경로 없음)이라, 통과가
"코드가 맞다"가 아니라 "오늘 방과 볼륨이 맞았다"를 뜻하는 상태였다.

방·스피커의 음향 자체가 더하던 것(잔향·룸 노이즈)은 **SNR 픽스처가 오프라인
에서 훨씬 통제된 형태로 이미 검증**한다. 즉 재생 소리가 사는 값은 음향이
아니라 "진짜 마이크로 들어온 샘플"뿐이었다.

## 무엇을 잃었나 (정직하게)

**실제 장치가 넘겨주는 샘플을 우리가 옳게 해석하는지** 확인하던 유일한
테스트였다. 이 구멍으로 지나갈 수 있는 결함:

- 장치가 "48000Hz"라 신고하고 실제로는 44100 으로 전달 → 표시가 전부
  **137¢** 어긋난다. 오프라인 테스트는 sr 을 우리가 직접 넘기므로 전부 통과.
- 스테레오 입력의 인터리브를 잘못 풀면 주파수가 배/반으로 읽힐 수 있다.
  `test_input_devices.py` 는 `ndim == 1` 만 보지 샘플이 옳게 풀렸는지는 못 본다.

즉 **앱 전체가 틀린 음을 표시하는데 스위트는 전부 초록**인 상태가 가능해졌다.
이 위험을 안고 지운 것이지, 위험이 없어서 지운 게 아니다.

## 재도전 조건

둘 중 하나가 생기면 되살릴 가치가 있다:

1. **소리 없는 루프백** — 가상 오디오 장치(VB-Cable, BlackHole)가 있는
   기계에서만 도는 형태. 같은 주장을 조용히·결정론적으로 검증한다.
   대부분의 기계에선 스킵될 테니 "있으면 돈다" 마커가 필요하다.
2. **샘플레이트 정직성 테스트** — 실제 장치를 몇 초 열어 도착한 샘플 수를
   벽시계와 대조한다. 위 두 결함 중 값나가는 쪽(레이트 불일치)을 소리 없이,
   방 상태와 무관하게, 2초에 잡는다. 인터리브까지는 못 본다.

2번은 이 항목과 무관하게 **지금 만들 수 있다** — 아직 안 만들었다.
