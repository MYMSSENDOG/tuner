# 정답 데이터 먼저 (Ground Truth First)

**언제 읽나**: 새 알고리즘/기능 영역에 들어갈 때, 새 테스트 데이터가
필요할 때, "정답을 어디서 가져오지?"라는 질문이 생길 때.

## 규칙

새 영역의 구현을 시작하기 전에 네 가지를 먼저 갖춘다:

1. **진실이라 말할 수 있는 테스트 데이터** — "학교종이 땡땡땡 수준이라도,
   몇 초부터 몇 초까지 몇 Hz 인지" 상세하게 기록된 데이터.
2. **그 데이터를 만들어 내는 능력** — 도구화되어 반복 가능해야 한다.
3. **그 데이터가 진실인지 검증하는 능력** — 정답 생성기 자신도 검증
   대상이다. 우리 코드 밖의 권위(수학적 유도, 제3자 라벨, 독립 구현,
   물리 법칙)와 대조한다.
4. **그 데이터로 앱을 채점하는 하네스.**

구현을 먼저 하고 테스트를 나중에 붙이지 않는다.

## 함정

정답 생성기와 앱이 로직을 공유하게 되면 "일치 = 정답"이 무너진다
(실례: `divide_to_true_f0` 공유). 공유가 불가피하면 문서에 명시하고
외부 권위로 감시한다.

현재 갖춰진 정답 체계(합성 신호 / 실악기 주석 / 제3자 라벨)와 그 신뢰
구조·실례는 `docs/pitch-pipeline.md` "정답의 신뢰 구조" 절이 원본이다 —
여기 중복하지 않는다.

## 현장에서 들어오는 데이터

코퍼스는 유한하고 고정이다. 남은 결함은 대부분 실연주에서만 나오므로,
앱이 마지막 10초를 링버퍼에 들고 있다가 **Ctrl+R** 로 리포트를 떨군다
(오디오 + 그때 표시된 트레이스 + 코드 sha, `~/.tuner/reports/<utc>/`).

```bash
python -m tuner.tools.promote <리포트>                  # 재현되는지부터 확인
python -m tuner.tools.promote <리포트> --name flute_flicker_C6
```

규칙 3(검증 능력)이 여기서도 적용된다 — 현장 오디오에는 정답이 없다:

- **먼저 재현 여부를 묻는다.** 저장된 오디오를 같은 파이프라인에 다시
  통과시켜 현장 트레이스와 프레임 단위로 비교한다. 같으면 코드의 문제라
  픽스처가 붙든다. 다르면 타이밍·장치 의존이라 픽스처로는 못 잡고,
  리포트 자체가 증거다.
- **라벨은 주석기가 만든다** (`--name` 을 주면 자동). 앱과 다른 알고리즘
  이라는 교차검증 구조는 그대로지만, 방 녹음은 잡음이 많아 깨끗한 기준을
  못 넘길 수 있다 — 그때는 이름에 `.snr` 을 넣어 완화된 기준으로 채점한다.
- 승격 전에 **고칠 결함을 실제로 잡는 테스트**부터 쓴다 (회귀 봉인 규칙).
